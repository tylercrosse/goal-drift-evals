For Lisa, regarding OCaml FFI bindings to a C++ pricing library:
Dealing with C++ FFI in OCaml, especially with complex data structures and memory management, can be tricky.
1.  **Ctypes.Structured vs. Manual Marshaling**:
    *   **`Ctypes.Structured`**: This is generally the preferred and more OCaml-idiomatic approach for passing structs, as it handles the memory layout and type safety automatically. If you're getting segfaults, the issue might not be `Ctypes.Structured` itself but rather:
        *   **Mismatch in C++ and OCaml struct definitions**: Ensure the field types, order, and padding exactly match between your C++ struct and your `Ctypes.Structured` definition. Even minor differences can cause segfaults.
        *   **Memory alignment**: C++ structs might have certain alignment requirements that need to be explicitly handled in `Ctypes`.
        *   **Memory ownership/lifespan**: Who allocates and deallocates the memory? If C++ expects to deallocate memory allocated by OCaml, or vice-versa, without proper handling, you'll get issues.
    *   **Manual Marshaling**: This involves manually converting OCaml data to a C-compatible memory block (e.g., using `Bigarray` or manually writing bytes) and passing a pointer to C++. It gives you maximum control but is highly error-prone and less safe. It should be a last resort if `Ctypes.Structured` cannot be made to work, perhaps due to highly unusual C++ memory layouts.
2.  **Memory Leaks and Finalizers (Gc.finalise)**:
    *   `Gc.finalise` is **unreliable** for critical resource management or ensuring memory is freed promptly, as you've observed. The OCaml GC is not deterministic about when finalizers run.
    *   **Explicit Resource Management**: For C++ objects allocated via FFI, you absolutely need **explicit resource management** from the OCaml side. This typically involves:
        *   Creating OCaml functions that explicitly call the C++ destructor or `delete` function via FFI.
        *   Ensuring these explicit deallocation functions are called deterministically when the C++ object is no longer needed (e.g., within an `Lwt.finally` or `try...with...finally` block, or through a resource-management library).
    *   **Smart Pointers in C++**: If your C++ library uses smart pointers (e.g., `std::shared_ptr`, `std::unique_ptr`), leverage them. You'd pass raw pointers to OCaml, but ensure the C++ smart pointer maintains ownership and handles deallocation when its reference count drops.
